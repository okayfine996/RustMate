# Feature Specification: 自动更新（Stable/Beta 渠道）

**Feature Branch**: `[005-sparkle-auto-update]`  
**Created**: 2026-01-05  
**Status**: Draft  
**Input**: 使用自动更新：客户端默认订阅 stable 更新源；用户在设置中打开“接收 Beta”后切换到 beta 更新源；发布产物为 DMG；每次发版需完成签名与公证；DMG 托管在 GitHub Releases，两个更新清单（appcast）托管在稳定 URL（GitHub Pages 或 raw）；在更新清单中声明最低 macOS 15；更新体验为后台下载，提示用户重启/退出安装；更新安全依赖 HTTPS 与更新包签名校验。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 从稳定渠道自动更新（Priority: P1）

作为普通用户，我希望应用能在后台检查并下载新版本，并在需要时提示我重启/退出完成安装，以便我能持续获得修复与改进且不被频繁打扰。

**Why this priority**: 这是所有用户都需要的核心价值（减少手动下载与版本滞后），也是“可交付的最小闭环”。

**Independent Test**: 提供一个稳定渠道的新版本条目后，应用能够发现更新、下载完成后提示安装、安装后版本变更可验证。

**Acceptance Scenarios**:

1. **Given** 用户未加入 Beta、当前版本低于稳定渠道最新版本，**When** 应用触发更新检查，**Then** 能发现更新并开始后台下载（不阻塞 UI）。
2. **Given** 更新已下载完成，**When** 用户选择“安装/重启”，**Then** 应用退出并在再次启动后运行在新版本。
3. **Given** 用户选择“稍后”，**When** 更新已下载完成，**Then** 不强制打断当前工作，但在后续合适时机仍可完成安装。

---

### User Story 2 - 用户选择加入/退出 Beta 渠道（Priority: P2）

作为希望提前体验新功能的用户，我希望在设置中打开“接收 Beta 更新”来加入 Beta 渠道，并能随时关闭回到稳定渠道，以便自主控制风险。

**Why this priority**: Beta 是明确需求，但其价值建立在 P1 的稳定更新闭环之上。

**Independent Test**: 切换开关后，应用后续更新检查应从对应渠道获取更新信息（可通过放置不同版本条目验证）。

**Acceptance Scenarios**:

1. **Given** 用户当前在 stable 渠道，**When** 打开“接收 Beta 更新”，**Then** 下次检查更新会使用 beta 渠道的更新清单。
2. **Given** 用户当前在 beta 渠道，**When** 关闭“接收 Beta 更新”，**Then** 下次检查更新会回到 stable 渠道更新清单。

---

### User Story 3 - 更新失败时给出可行动的反馈（Priority: P3）

作为用户，当更新检查或下载失败时，我希望看到清晰、可操作的提示（例如网络问题、更新源不可用、更新包校验失败），以便我能理解原因并采取行动。

**Why this priority**: 降低支持成本与用户困惑，提升对自动更新的信任；但可在 P1/P2 完成后交付。

**Independent Test**: 通过断网、提供无效更新条目、或返回不可访问 URL，验证错误提示与恢复方式。

**Acceptance Scenarios**:

1. **Given** 网络不可用，**When** 检查更新，**Then** 显示“无法检查更新（网络问题）”且不影响其它功能使用。
2. **Given** 更新清单可访问但更新包校验失败，**When** 下载后尝试安装，**Then** 明确提示“更新包无效/已被篡改”，且不会安装该更新。

### Edge Cases

- 当用户系统版本低于 macOS 15 时：不得提示可安装的更新（即使渠道存在新版本），并给出“需要更高系统版本”的解释。
- 当更新清单不可访问/响应超时：应快速失败并可重试，不应卡住 UI。
- 当更新包下载中断：应支持恢复/重试，不应导致持续错误状态。
- 当用户正在执行长任务时：提示安装应避免突然中断，允许“稍后”。
- 当更新条目版本号异常（例如降级、重复、缺字段）：应安全失败并记录可诊断信息。

## Requirements *(mandatory)*

### Constitution Constraints (mandatory)

- **No-default-XPC**: 本功能默认不引入/依赖 XPC；自动更新在应用进程内完成。
- **Sandbox & Security**: 更新源必须为 HTTPS；更新清单与更新包 URL 必须为受控来源；任何外部输入（URL/版本字段）必须做校验与降级处理；安装过程不得请求超出必要范围的权限。
- **Structured Results**: 更新相关状态/错误必须以结构化方式建模（例如：成功/失败、错误类型、建议动作），UI 不依赖多行原始文本作为协议。

### Functional Requirements

- **FR-001**: 系统 MUST 默认从“稳定渠道更新清单”检查更新，并在发现新版本时后台下载更新。
- **FR-002**: 系统 MUST 在更新下载完成后提示用户“退出/重启后安装”，并允许用户选择“稍后”。
- **FR-003**: 系统 MUST 提供“接收 Beta 更新”设置项；开启后 MUST 使用 Beta 更新清单；关闭后 MUST 回到稳定更新清单。
- **FR-004**: 系统 MUST 在更新清单中声明并遵守最低系统版本（macOS 15.0）；对低于该版本的系统 MUST 不提供可安装更新。
- **FR-005**: 系统 MUST 验证更新的真实性与完整性（校验失败 MUST 阻止安装并给出可行动提示）。
- **FR-006**: 系统 MUST 在更新检查/下载失败时给出用户可理解、可行动的错误提示，并允许重试（不影响核心功能使用）。
- **FR-007**: 系统 MUST 记住用户选择的更新渠道偏好（重启后仍生效）。

### Key Entities *(include if feature involves data)*

- **UpdateChannelPreference**: 表示用户当前选择的更新渠道（stable / beta）。
- **UpdateFeed**: 表示一个更新清单来源（固定 URL、渠道类型、最低系统版本约束）。
- **UpdateState**: 表示更新流程状态（未检查/检查中/有更新/下载中/可安装/失败 + 错误类型）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在正常网络环境下，更新检查在 3 秒内给出“有更新/无更新/失败”的明确结果（不阻塞 UI）。
- **SC-002**: 对可用更新，后台下载完成后用户能在 2 次点击以内完成“退出/重启并更新到新版本”。
- **SC-003**: 用户切换 stable/beta 渠道后，下次检查更新即可按新渠道生效（无需重装应用）。
- **SC-004**: 对“更新清单不可用、网络失败、校验失败、系统版本不满足”等主要失败类型，用户界面均提供清晰原因与可执行下一步（重试/手动下载/升级系统等）。
